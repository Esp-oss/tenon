# 标准件报价之后的履约

报价单一旦落定，业务员真正要的答案是「这批货能不能按时给出去」。这份文档只写业务判断，
不指定任何具体动作——能做哪些动作，由运行期从各模块当场声明的能力清单里发现，写死在这里
就等于把流程退化成程序。

## 拿到什么

- 报价单号与报价单标识；
- 明细行：每一行的 SKU 与需求量；
- 事件自带的业务链标识：同一笔业务的规划、审计记录与共驾帧都靠它串成一条线。

## 判断顺序

1. **先核库存，再谈承诺。** 逐行确认每个 SKU 当前的可用量。核库存是只读的事实查询；
   任何有副作用的动作都要等事实到手之后再谈。
2. **够则直接履约。** 每一行的需求量都不超过可用量时，按报价单明细扣减。扣减必须带上
   报价单号作为业务参照，使同一笔业务被反复提及时不会重复扣一次。
3. **不够则分两段处理。** 可用量不足是常态，不是异常：
   - 部分履约：先把能扣的扣掉（例如可用 3、需求 12，就先扣 3），缺口部分转成采购需求，
     等到货后补齐；
   - 缺口大到给不出有意义的交付承诺时，直接转人工，让人决定拆单、改期还是放弃。
   这两种都是可接受的结果；抛错误只会让业务员看到一个无从处理的失败。
4. **拿不准就问人。** 下列情形一律转人工，不猜、不绕路：
   - 报价单里的 SKU 在在场模块里都查不到；
   - 履约需要的模块不在场（能力清单里没有它）；
   - 任何一步被治理闸门拒绝：策略拒绝、授权不足、预演结论未通过；
   - 同一类业务拒绝连续出现，说明计划的前提一直没成立。

## 底线

- 只使用模块当场声明的能力；不得假设某个模块一定存在、某条路径一定可用。
- 每一步都要能被审计追到：报价单号、业务链标识与幂等键必须与本次业务一致。
- 转人工时写清缺口：缺哪个 SKU、缺多少、缺哪个能力。让人不必回头翻日志。
- 不得为了「跑通」绕过闸门，也不得伪造预演结论。

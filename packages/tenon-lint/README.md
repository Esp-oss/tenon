# @tenon/lint

C10 反模式 AST 扫描器：检查接入方仓库里是否把「事件 → action」「错误码 → action」写成了代码映射。

## 职责边界

- 负责三条扫描规则（§10.2 C10）：
  1. 事件订阅回调体内出现具体 action 字面量（`actions.<id>`、`invoke("<module>.<action>")`）。
  2. 错误码到 action 的映射（如 `case STOCK_INSUFFICIENT: call(...)`）。
  3. skill 正文里出现 `模块.action` 形式的动作标识符（§6.4 硬约束）。
- 负责：可对任意接入方仓库运行（不限于本仓库），命中任一条即失败。
- 不负责：不做差异测试（D1 属 `@tenon/conformance`），不判定运行时行为，不做性能/风格 lint（ESLint 的职责），不改写源码。
- 不负责：不做自动修复。反模式是设计问题，机器只能报警，不能替接入方重新设计。

**已知限制（包自己声明）**：只覆盖 TS/JS 的 AST。非 TS 接入方（Python/Java 等）无法被本包扫描，只能靠 D1 差异测试兜底——这也是 D1 是主判据、本包是辅助判据的原因（§10.2、D13）。

## 依赖

- 对 dsh：**无依赖**，不 import cordis。扫描器要能跑在任意接入方仓库，被 dsh 绑住会限制其适用范围（§9「协议层不 import dsh」）。
- 包间依赖：不依赖其他 `@tenon/*` 包。规则 1、2 的判据来自 §2.2 反模式判据，规则 3 的判据来自 §6.4，均为规范文本，不需要引入 `@tenon/core` 的类型。
- 第三方依赖：当前 `peerDependencies` 为空；M0 实现 AST 扫描时需要 TS 编译器 API 或等价解析器。

## 阶段状态

M0（当前）：只有骨架，未实现。M0 计划实现三条规则、可对任意仓库运行，并作为 M0 出口判据之一（§12：D1 与 C10 全绿）。

M1 计划把规则命中项与治理侧的审计/策略数据对齐（例如把命中位置写进审计备注），但不新增扫描规则——三条规则的判据由 §2.2 与 §6.4 冻结。

M2 计划随 HTTP 侧车发布，为非 TS 接入方提供规则说明文档与手工自查清单；本包仍只做 TS/JS，跨语言一律由 D1 差异测试兜底。

M3 计划把规则 3 扩展到 skill 仓库的发布前检查（§6.4、D8：单人可发布但发布进审计），与 `@tenon/dsh-plugin-skill-biz` 共用同一规则实现。

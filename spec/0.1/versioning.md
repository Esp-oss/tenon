# 版本演进与兼容（§4.10、§9）

协议的演进规则本身是可机械验证的：**只增不删、未知字段忽略、major 不兼容**。任何一条被破坏，第三方实现就无法在不与全网同步升级的前提下继续互通，而「模块可插拔」正是本协议存在的理由。

---

## 1. 三个版本号，别混用

| 版本 | 形如 | 谁持有 | 在哪出现 |
|---|---|---|---|
| **协议版本** | `0.1`（`major.minor`，无第三位） | 协议规范本身 | `Tenon-Version` / `Tenon-Min-Version` 请求头；`ModuleManifest.tenon` |
| **契约版本** | `1.4.0`（语义化版本） | 每个 action / event / module | `Action.version`、`DomainEvent.version`、`ModuleInfo.version` |
| **实现版本** | `0.3.2` | 某个具体实现（库、插件、侧车） | 该实现自己的包元数据，不属于协议报文 |

三者互不推导：协议 `0.1` 之上可以有无数 `1.x` 的 action 契约。契约版本由模块自己演进，协议只规定**怎么演进才不破坏互通**。

---

## 2. 协议版本的语义

- 协议版本只有 `major.minor`：`0.1`、`0.2`、`1.0`。
- **major 不等即不兼容**：`0.x` 与 `1.x` 之间不承诺任何互通性，包括字段名与语义。
- **minor 递增即向后兼容**：`0.2` 的消费方必须能处理 `0.1` 的报文（因为只增不删）；`0.1` 的消费方必须能处理 `0.2` 的报文（因为未知字段被忽略）。
- **纯文档澄清不升版本**：如果一次改动不改变任何可机械验证的行为（只把一句含糊的描述写清楚），不升版本号，只更新 [`CHANGELOG.md`](CHANGELOG.md)。一旦改动改变了断言结果，就必须升 minor。

---

## 3. 三条硬规则

### 3.1 只增不删

任何已发布的字段、枚举值、端点、状态名**不得删除、不得改名、不得改变含义**。唯一允许的移除途径是 major 升级（见 §6 弃用流程）。

### 3.2 未知字段必须忽略

消费方解析报文时，遇到本版本不认识的字段必须**忽略并继续**，不得因为未知字段拒绝报文（§4.10）。这是前向兼容的唯一实现方式。

`README.md` §5 已说明：schema 里的 `additionalProperties: false` 是**给生产方自检**的封闭声明，与消费方的容忍义务不冲突。反例用例 C3 就测这一点：向合法报文注入未知字段，断言消费方正常处理。

### 3.3 新增的必须是「可缺失」的

一次 minor 升级新增的字段，必须满足以下之一：

1. 有明确的缺省语义（省略等价于某个值，例如 `Action.deprecated` 省略即 `false`）；
2. 缺失时整个特性降级而不是失败（例如新增的 `ModuleManifest.unavailableActions`，旧生产方不给，消费方视为「全部可用」）。

新增**必填**字段是 major 变更，不是因为旧消费方读不懂，而是因为旧**生产方**无法产出合法报文——那会立刻让所有未升级的模块失去资格。

### 3.4 新增枚举值需要降级路径

枚举在 schema 里是封闭的（这是为了让生产方无法写错字），但它仍然可以在 minor 版本里扩展。消费方遇到未知枚举值时：

| 场景 | 处理 |
|---|---|
| 未知 `duplicateBehavior` | 按 `return_first_result` 处理（唯一的兼容安全值） |
| 未知 `dryRun.status` | 按 `pending` 处理（强制审批，fail-closed） |
| 未知 `transports` / `capabilities` 取值 | 忽略该项 |
| 未知 `Error.class` | 按 `contract_violation` 处理（死信 + 告警，不重试） |

原则是统一的：**未知值一律落到最保守的解释**，绝不落到「照旧执行」。

## 4. 版本协商：请求头

| 头 | 谁发 | 含义 |
|---|---|---|
| `Tenon-Version: 0.1` | 双方都发 | 本方实现的协议版本 |
| `Tenon-Min-Version: 0.1` | 双方都发 | 本方愿意与之互通的最低对端版本 |

### 4.1 判定规则

1. **major 必须相等**：`对端.major != 本方.major` → 不兼容。`Tenon-Version: 0.1` 的实现不允许与 `1.x` 的对端通信，反之亦然。
2. **minor 可以不同**：双方按 `min(双方 minor)` 的语义解释报文。高版本方不得让「低版本方看不懂的字段」承载必需信息（§3.3）。
3. **越界即拒**：`对端.version < 本方.minVersion`，或 `本方.version < 对端.minVersion` → 拒绝。

### 4.2 拒绝时怎么回

- 返回 `contract_violation`（HTTP 400，见 [`errors.md`](errors.md) §5）。
- 响应头带上本方的 `Tenon-Version` 与 `Tenon-Min-Version`，让对方知道该升级到哪。
- **不得「尽力而为」地继续处理**：版本不匹配意味着状态机与执行语义可能不同，继续跑等于在没有共识的前提下产生副作用。

### 4.3 头缺失

缺少 `Tenon-Version` 视为 `0.1`（0.1 期唯一的实现版本）；缺少 `Tenon-Min-Version` 视为与 `Tenon-Version` 相同。这是为了让 0.1 的最小实现不必处理协商，但仍然可以被协商。

## 5. 兼容性判定表

对每一次具体改动，按下表定位版本位。表里「兼容」指「未升级的对端仍能正确工作」。

| 变更 | 协议位 | 兼容 | 理由 |
|---|---|---|---|
| 新增可选字段 | minor | 是 | 旧消费方忽略（§3.2），旧生产方不产出（§3.3 需有缺省语义） |
| 新增枚举值 | minor | 是 | 旧消费方按 §3.4 降级 |
| 新增端点 | minor | 是 | 旧实现不实现它，特性降级（如 dry-run 缺失 → 强制审批） |
| 新增一份契约（第 10 类） | minor | 是 | 未实现的契约不参与互通 |
| 放宽校验（如 `minLength` 变小） | minor | 是 | 旧的合法文档仍然合法 |
| 纯文字澄清、无语义变化 | 不升版 | 是 | 只改文档，断言不变 |
| 删除字段 | major | 否 | 旧生产方仍在发，旧消费方仍在读 |
| 新增必填字段 | major | 否 | 旧生产方立刻不合法 |
| 收窄校验（`pattern` 变严、新增 `required`、新增 `if/then`） | major | 否 | 旧的合法文档变非法 |
| 改字段语义（同名不同义） | major | 否 | 最危险的一种：不报错但算错 |
| 改状态机状态集合或迁移边 | major | 否 | 双方对「现在能不能执行」判断不同 |
| 改执行语义默认值（重试/熔断/超时） | major | 否 | 可观测行为变化，且旧实现无从得知 |
| 改错误分类的判定归属 | major | 否 | agent 的应对策略会变（重试 vs 改路） |
| 删除契约或端点 | major | 否 | 等同于删除字段 |

**收紧与放宽不对称。** 放宽是 minor，收紧是 major——这是「只增不删」在约束层面的必然推论：收紧等于对外宣称「你以前合法的东西现在不合法了」，与删除字段同性质。

## 6. 弃用流程

弃用是**两个版本位上的两段动作**，中间必须留足一个 minor 的迁移期。

### 6.1 第一段：标记（minor N）

1. 在 schema 层面标记：可标记的字段用 `deprecated: true`（如 [`Action.deprecated`](schemas/action.schema.json)）；若为整份契约或端点，在对应 schema 的 `description` 里写明弃用与替代路径。
2. 在 [`CHANGELOG.md`](CHANGELOG.md) 的 `### Deprecated` 段记录：弃用对象、替代方案、计划移除的版本。
3. **行为不变**：被弃用的字段/枚举值/端点必须继续被接受并正确处理。弃用是通知，不是失效。
4. 一致性用例继续覆盖它，直到移除那一版——否则实现方会以为已经可以不管。

### 6.2 第二段：移除（major N+1）

1. 只有 major 升级才能真删除。删除后，旧生产方发来的该字段变成「未知字段」，被新消费方忽略（§3.2）。
2. `CHANGELOG.md` 的 `### Removed` 段记录，并指明上一版已弃用。
3. 移除必须伴随迁移说明：替代字段是什么、旧数据怎么解释。

### 6.3 为什么必须留一个 minor

模块是独立部署的：协议升级不是一次全网发布，而是「谁先升级谁先受益，没升级的必须照常工作」。如果一个 minor 内标记并删除，就退化成强制同步升级——这正是协议要避免的。留一个 minor 的含义是：**任何人都至少有一次发布窗口来改掉它**。

### 6.4 契约自身的版本（action / event / module）

契约走语义化版本，与本文件的规则同构：

| 契约变更 | 版本位 |
|---|---|
| 新增可选入参/出参字段 | minor |
| 新增错误码 | minor |
| 删除字段、收紧入参校验、改语义 | major（并以新 `id` 并行发布，不原地改名） |

`id` 一旦发布不改名：破坏性变更发布为新 `id`（例如 `inventory.DeductStockV2`）或新 major 版本，二者并存一段时间，由发现结果同时宣告。

### 6.5 skill 与业务知识

skill（业务流程知识）同样版本化（`version: 1.2.0`），发布进审计、可一键回滚（§6.4 D8）。知识与协议的区别是：skill 不进一致性测试（它不含线格式），但它的正文受反模式 lint 约束（不得出现 `模块.action` 形式的动作标识符）。

## 7. 变更的落地流程（与 CI）

1. 改 schema（唯一真源）。
2. 跑 `node scripts/validate-spec.mjs`：结构、`$id`、引用完整性。
3. 跑一致性测试套件：`conformance/` 的 C1–C10 + D1，断言语义未被改动破坏。
4. 按 §5 判定版本位，更新 `Tenon-Version` 相关文档与 [`CHANGELOG.md`](CHANGELOG.md)。
5. 若为弃用或移除，按 §6 执行两段动作。

CI 必须跑第 2、3 步（§8 #7「版本演进：只增不删、未知字段忽略、一致性测试进 CI」）。**没有跑过一致性测试的版本不得发布**：一个「看起来只是改了描述」的改动，可能已经让某个断言失败。

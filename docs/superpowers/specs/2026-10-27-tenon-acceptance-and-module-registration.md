# 验收定义与模块注册需求（R1–R3 / Q1–Q3）

- 日期：2026-10-27
- 状态：需求已确认，**方案待设计**（R1 与 R2 的落地路径都还没定）
- 来源：项目所有者口述需求（2026-10-27），本文只做**忠实记录与结构化**，不替所有者做技术选型
- 关联：[ADR-0001](../../adr/0001-driver-dsh-vs-go.md) §6 落地顺序；现状审计结论见文末 §5

## 1. R1：新业务模块应**动态注册 + 健康检查**，主动申报能力与入口

**需求**：新业务模块上线时**主动向系统申报**自己的能力与入口，系统据此发现它；模块下线/失联时系统应能感知并摘除。

**为什么现在是问题**（现状取证）：

| 现状 | 证据 | 后果 |
|---|---|---|
| 生产注册靠启动环境变量 | `cmd/host/main.go`：`TENON_MODULES=id=url,id=url`，解析失败即退出 | 新模块上线 = **改环境变量 + 重启控制平面** |
| 动态注册端点仅测试态 | `POST /tenon/admin/modules` 只在 `TENON_TEST_MODE=1` 挂载（启动打警告） | 生产没有注册入口 |
| 能力发现是「拉」不是「报」 | agent `discover()` → `GET /tenon/modules` → 逐模块 `GET /.well-known/tenon` | 模块自己不知道有没有被看见；没有任何心跳/健康语义 |
| 摘除只能靠人工开关 | `registry.SetEnabled(id,false)`（D1 用它模拟摘除） | 模块崩溃后 host 仍认为它在场，回合会打到死地址 |

**要求（供后续设计对齐，不是方案）**：

> **方案已成文**：[`2026-10-27-tenon-module-registration-design.md`](2026-10-27-tenon-module-registration-design.md)——全 push（注册 + 心跳 TTL）、人工 disable 粘性、心跳带声明哈希（不匹配重申报）、注册事件独立 append-only 链。本文 R1 段保留为需求原文。

1. 模块**主动申报**：把自己的能力（actions/events/摘要）与入口推给系统，而不是等系统来拉；
2. **健康检查**：系统能判定模块「在线/失联」，失联后**自动摘除**（对应 `enabled=false` 的那条既有语义），恢复后自动回归；
3. 申报/心跳要**可审计**（谁在什么时候上线、下线），不能是静默状态变更；
4. 不能削弱既有不变量：策略仍 fail-closed、审计仍是两段写、注册表仍是「agent 可见性的唯一来源」。

**明确不在本条内**：模块自动发现网络位置（服务发现）、多副本负载均衡、灰度发布。

## 2. R2：最终验收以 **DSH 为驱动**来操作业务，包含**对话页面**

**需求**：最终形态下，操作员在 **DSH 的对话页面**里说一句话，由 **DSH 驱动**完成业务操作（规划 → 闸门 → 审批 → 执行 → 审计），而不是由 Go agent 驱动。

**验收口径（可机械验证的最小集合，先立靶子再谈实现）**：

| # | 步骤 | 判定 |
|---|---|---|
| A1 | 在 DSH 对话页输入「扣 12 件 STD-1001」 | DSH 产出计划（可回放），不是 Go agent 的计划 |
| A2 | 计划命中 `approve` 策略 | 出现待批（入口可以是 DSH 的审批 UI） |
| A3 | 由 bob 批准 | 批准后**库存真的减少**、审计 `result` 段带 `approvedBy=user:bob` |
| A4 | 事后查询 | 能按 `planId` 查到两段审计，且能追溯到**发起人**（非 agent 自身） |
| A5 | 审计链 | `prevHash` 连续，未因经过 DSH 而断链 |

**三个开放问题（Q1–Q3，本条不解决，必须先定）**：

### Q1 工作区（workspace）怎么管

- 一个操作员可能属于多个工作区（如「华东仓」「华南仓」），业务数据按工作区分区；
- 待定：工作区是 DSH 会话的一个属性、还是 Tenon 身份声明的一部分？跨工作区的操作要不要二次确认？
- 影响：审计的 `actor` 与实体寻址都要能落到工作区，否则「同一个人在两个仓各扣一次」无法区分。

### Q2 操作员身份怎么绑定

- Tenon 已有：`POST /tenon/session` 发 token，`onBehalfOf` 进审计；
- DSH 已有：会话级身份、（本会话观察到的）permission/approval 按 session 生效；
- 待定：**以谁为准**？建议方向（未决）：DSH 会话为「是谁在打字」的事实源，Tenon token 为「能做什么」的事实源，两者在 adapter 里显式绑定，**审计同时记录两者**，不做隐式映射；
- 硬约束：审计必须能回答「是哪个人按的」，不能只写「agent 做的」——否则审批链路无意义。

### Q3 历史会话怎么查看、怎么隔离

- 待定：历史会话的**可见范围**（只有本人？同工作区可见？）与**存储位置**（DSH 会话存储 vs Tenon 审计）；
- 已知冲突：DSH 的会话是「对话记录」，Tenon 的审计是「业务事实」，两者粒度不同（一个回合可能产生多笔业务，一笔业务可能跨多个回合）；
- 硬约束：**业务事实以 Tenon 审计为准**，DSH 会话只是叙述层；查看历史时不得把「对话里说过的」当成「业务上发生过的」。

## 3. R3：**业务事件触发仍然保留**，由 DSH 驱动按流程操作其他业务

**需求**：不能因为换成「对话驱动」就丢掉事件驱动。业务事件（如 `quote.completed`）到达后，仍要能自动开回合，由 **DSH** 按业务流程去操作**其他模块**（如 `inventory`、`procurement`）。

**已有的正确语义（不要再改）**：

- 事件订阅（skill 的 `tenon.subscribes`）**只决定「是否开启一个回合」，不决定「做什么」**（设计文档 §2.2）；
- 做什么必须由规划 + 闸门决定，且闸门结论与来源无关（不能因为「是事件来的」就放宽）。

**本条新增的只是**：回合的执行者从 Go agent 换成 DSH；且事件回合与对话回合**共享同一套闸门、审计与公告板**（不能出现两套真相）。

**验收口径**：

| # | 步骤 | 判定 |
|---|---|---|
| B1 | 投一个 `quote.completed`（走模块发件箱或注入） | DSH 侧开了一个回合（而不是 Go agent） |
| B2 | 计划里出现**其他模块**的动作（如 `procurement.CreatePurchaseRequest`） | 说明它按流程跨模块操作，而非只读原模块 |
| B3 | 审计 | 两段写齐全、`correlationId` 串起事件与计划、审批（若命中 approve）落在公告板 |

## 4. 三条需求之间的关系

```
R3（事件触发） ─┐
                ├─► 同一个回合执行者：DSH（R2）
R2（对话触发） ─┘        │
                          ├─ 闸门/审计/公告板：仍是 Go 控制平面（ADR-0001 §2）
                          └─ 模块从哪来：R1 的动态注册 + 健康检查
```

- R1 是**供给侧**：让「新业务」能被系统看见；
- R3 与 R2 是**触发侧**：两条入口，一个执行者；
- 三者叠加才是最终验收：**新模块自动上线 → 事件或人触发 → DSH 规划 → 闸门 → 执行 → 审计可追到人**。

## 5. 与现状的距离（审计结论，2026-10-27）

| 能力 | 今天 | 目标 | 差距性质 |
|---|---|---|---|
| 模块发现 | host 环境变量 + 重启；拉 manifest | 动态申报 + 心跳 + 自动摘除 | R1：要设计 |
| 回合执行者 | **Go agent** | **DSH** | R2：0 实现（全仓 0 行 dsh 代码） |
| 对话入口 | 自制静态页（已冻结为 demo） | DSH 对话页 | R2：0 实现 |
| 事件触发 | skill `subscribes` → Go agent 回合 | 同语义，执行者换成 DSH | R3：语义已在，执行者要换 |
| 身份与工作区 | Tenon token + roles；无工作区概念 | 身份绑定 + 工作区 | Q1/Q2 未决 |
| 历史会话 | Tenon 审计（业务事实）+ DSH 会话（叙述） | 明确可见范围与隔离规则 | Q3 未决 |
| 审批真相 | 公告板（已实现） | 不变 | 无差距 |

**结论**：R1 与 R2 都是**未开始**的工作；R3 的协议语义已具备，缺的是「把执行者换成 DSH」；Q1–Q3 是 R2 的前置决策，**必须先定，否则 R2 的验收无从判定**。

三条候选架构：协议住在哪一层？

三条都满足「模块可插拔 + AI 驱动」，差别在**协议与运行时的绑定关系**——这决定了兼容性和健壮性的上限。点击选一条。

A

协议网关中心（Gateway-centric）

 [业务事件]   [HTTP/Webhook]   [MCP]
     ↘             ↓            ↙
   ┌────────────────────────────────┐
   │  Protocol Gateway  (语言无关)   │  ← 独立部署的进程
   │  registry · 授权矩阵 · 策略      │
   │  approval · audit · 幂等/对账    │
   └───────────────┬────────────────┘
                   │ 结构化 tool 调用
          ┌────────▼────────┐
          │  dsh Agent 内核  │
          └────────┬────────┘
                   │ HTTP
        ┌──────────▼──────────┐
        │ 业务模块（任意语言）  │
        └─────────────────────┘

协议住在网关里：模块只认网关，网关把能力喂给 agent。治理与协议同址，天然可独立部署、可被非 dsh 的 agent 复用。

换来

  • 协议边界最清晰，非 TS 系统只对接一个 HTTP 面
  • 治理可脱离 dsh 独立演进

代价

  • 多一跳；网关与 dsh 插件树两套状态
  • 治理逻辑容易两边都写一半
B

dsh 原生插件树（Everything is a plugin）

 [业务事件]  [HTTP]  [MCP]     ← 每个入口都是一个 cordis 插件
     ↘         ↓       ↙
   ┌──────────────────────────────┐
   │      cordis 插件树（单进程）   │
   │  module-adapter  governance   │
   │  skill           intent-ui     │
   │  policy          audit         │
   └───────────────┬──────────────┘
                   │ sidecar
        ┌──────────▼──────────┐
        │ 非 TS 业务系统        │
        └─────────────────────┘

协议 = 插件间 service 契约。最贴合「万物即插件」：零胶水、HMR 热插拔、直接复用 dsh 的 skill / token-meter / otel / session 审计。

换来

  • 最少的自研代码，最快跑通纵切面
  • 复用 dsh 全部治理原语

代价

  • 规范会渗进 dsh 细节，「别人只按协议接入」变得困难
  • 单进程心智：dsh 是单点，跨主机扩展弱
C

协议内核 + 多运行时（Spec-core，Recommended）

 ┌───────────────────────────────────────────────┐
 │ 协议内核（与运行时无关的契约 + 一致性测试套件）  │
 │  Action · Event · Intent/Confirm · Audit       │
 │  Approval · Policy · Idempotency               │
 └───────────────────────────────────────────────┘
        ▲              ▲               ▲
        │实现#1        │实现#2         │实现#3
 ┌──────┴─────┐ ┌──────┴──────┐ ┌──────┴───────┐
 │ dsh 原生    │ │ HTTP sidecar │ │ 第三方运行时  │
 │ cordis 插件 │ │ SDK(任意语言)│ │ 只需过一致性  │
 └──────┬─────┘ └──────┬──────┘ └──────────────┘
        └───────┬──────┘
        业务模块（任意语言/框架）

 控制平面（registry｜授权矩阵｜策略｜审计｜skill）不依赖任何运行时

协议住在规范里，dsh 只是第一个宿主。A 与 B 都是它的两个剖面：B = 参考实现#1，A = 参考实现#2 的网关形态。规范每条都配可执行一致性测试。

换来

  • 兼容性最高：任何语言/框架只按契约实现即可接入
  • 健壮性可度量：一致性测试是机械门禁，不靠自觉
  • 控制平面与数据平面分离，审计/策略不会散落在业务里

代价

  • 抽象成本最高，必须先死守「协议内 / 协议外」的边界
  • 写得松就成了空泛标准 —— 必须用测试套件兜住

我的建议：C 为终态，落地顺序是 B（先用 dsh 插件跑通「报价→扣库存」纵切面）→ 抽出一致性测试套件 → 补 A 的跨语言网关。这样第一周就有能跑的东西，协议也不会长成 dsh 的方言。

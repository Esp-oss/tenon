架构方案对比1 分层与契约2 纵切面时序3 健壮性

纵切面：报价完成 → 扣库存，13 步里 4 个闸门

配色：绿=业务模块 · 蓝=agent · 紫=控制平面/闸门 · 橙=人。注意 T2：agent 收到的不是「要执行的动作」，而是「一个事实 + 一个回合」。

T0 报价　业务员在页面完成标准件报价（quote-module 内部事务）
T1 出事件　quote.completed 经 outbox 投递（至少一次 · 可重放 · 带 causation/correlation）
T2 开回合　agent 收到事实，不是执行 handler：渲染上下文 = 事件 + 该领域 skill 索引 + 可用能力摘要
T3 取知识　加载 skill quote-to-fulfillment@1.2：标准件报价完成后须核库存并预留/扣减
T4 能力发现　/.well-known/asip 拿到 inventory-module 的 action 清单，只为要用的 action 拉完整 schema（省上下文）
T5 规划　产出 Plan DAG：GetStock → DeductStock(idemKey, compensation=ReleaseStock)，附 expectedDiff: onHand 120→108
T6 dry-run　模块 :dry-run 返回真实预演（无副作用）；模块未实现则 Plan 标注 unverified，自动升级为需审批
T7 闸门①策略　policy.evaluate(plan) → auto / approve / deny。金额或数量超阈值、或 reversible=false → 转人工
T8 闸门②授权　grant 矩阵：该 agent 身份是否有 inventory.DeductStock 权限（模块侧还会再拒一次）
T9-10 幂等执行　按拓扑序执行，每步带幂等键；模块自校验前置条件（够不够减是它说了算）→ 落地 → 模块独立写自己的审计 → 发 stock.deducted
T11 审计　写不可变审计事件：planId / stepId / 审批人 / inputHash / 结果 / 令牌用量
T12 共驾　Intent 帧 → 前端：open(quote#Q-123) + highlight(库存 −12 · 可撤销)；人点「撤销」→ 生成补偿 Plan 再走一遍闸门
T13 对账　审计里的「声称 diff」vs 模块终态，日切比对；不一致即告警

失败路径才是重点：错误分类决定 agent 能不能自救

规范必须定义错误分类，否则"AI 驱动"会退化成"抛异常给人"。

错误类例子agent 该做什么可否重试
retryable网络抖动 / 限流 / 超时按退避策略自动重试，幂等键不变是
business_rejection库存不足 / 单据状态变了重新规划：改预留、拆单、通知采购；拿不准就问人否
policy_denied超授权 / 超阈值 / 策略拒绝终止并转人工，不得换条路绕过否
contract_violationschema 不符 / 未知 action进死信队列 + 审计告警，这是接入方或协议 bug否

模块要接进来，最少只做这些

HTTP 侧车（任意语言 · 6 个端点）
GET  /.well-known/asip            → manifest
GET  /asip/actions/{id}           → schema + risk
POST /asip/actions/{id}           → 执行（Idempotency-Key）
POST /asip/actions/{id}:dry-run   → 预演（可选但强烈建议）
POST /asip/events                 → agent 收事件（Webhook 签名）
GET  /asip/events?since=cursor    → 补课/重放
dsh 原生（TS · 参考实现#1）
export const mod = defineModule({
  id: 'inventory',
  actions: [deductStock, releaseStock],
  events:  ['stock.deducted'],
})
ctx.plugin(asipModuleHost, mod)
// 自动挂成 dsh tool + 事件订阅 + 审计
// HMR 热插拔，不重启

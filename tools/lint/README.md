# tools/lint（Go）

C10 反模式扫描器：检查接入方仓库里是否把「事件 → action」「错误码 → action」写成了代码映射。

## 职责边界

- 负责三条扫描规则（§10.2 C10）：
  1. 事件订阅回调体内出现具体 action 字面量（`actions.<id>`、`invoke("<module>.<action>")`）。
  2. 错误码到 action 的映射（如 `case STOCK_INSUFFICIENT: call(...)`）。
  3. skill 正文里出现 `模块.action` 形式的动作标识符（§6.4 硬约束）。
- 负责：可对任意接入方仓库运行（不限于本仓库），命中任一条即失败。
- 不负责：不做差异测试（D1 属 `conformance/`），不判定运行时行为，不做性能/风格 lint（那是各语言 ESLint / golangci-lint 的职责），不改写源码、不做自动修复——反模式是设计问题，机器只能报警。

**已知限制（包自己声明）**：任何静态扫描都只能覆盖它能解析的语言。本工具只做 TS/JS 源码与 Markdown 正文，其他语言的接入方只能靠 D1 差异测试兜底——这也是 D1 是主判据、本工具只是辅助判据的原因（§10.2、D13）。

## 为什么用 Go 而不是 Node

- **交付形态决定**：接入方要在自己的 CI 里跑它。单文件二进制、交叉编译、无运行时依赖，接入成本接近零；`npx` 形态要求对方先有 Node 与网络。
- **不引入 cgo**：精确解析 TS/JS 的现成方案是 tree-sitter，但它要 cgo，会毁掉「单文件二进制 + 任意交叉编译」。所以实现路线是**纯 Go 词法扫描**：剥离字符串与注释 → 跟踪括号深度定位回调体 → 在体内匹配 action 字面量。对这三条规则够用；精度不足时才考虑 cgo 方案，并接受分发代价。
- **代价**：词法方案会有误报。缓解手段是行内豁免注释（`// tenon-allow: <理由>`）与规则白名单；但**误报率是 M0 的验收指标之一**，见下。

## M0 的验收方式（正反对拍）

扫描器不能只有「我实现好了」这一种说法，必须两边都测：

1. **真阳性**：造 3 个坏例（三条规则各一），必须全部命中，且报告里给出文件、行号、命中的规则号。
2. **零误报**：对 `demo/mini-erp` 与 `packages/` 全量扫描必须零命中——demo 里明确包含「库存不足时改走采购」的**技能描述**，那属于合法知识，不能被规则 3 误判。
3. **可豁免**：带 `// tenon-allow` 注释的行必须不报，且豁免本身进审计（谁在什么时候放行了什么）。

## 依赖

- 对 dsh：**无依赖**，不 import cordis。扫描器要能跑在任意接入方仓库，被 dsh 绑住会限制其适用范围（§9「协议层不 import dsh」）。
- 对 Node：**无依赖**。只读取源码文本，不需要目标项目的工具链。
- 仓内依赖：被 `conformance/` 调用（C10）；自身不依赖其他包——三条规则的判据来自 §2.2 与 §6.4 的规范文本。
